# System Design: Payment System (Stripe)

## 1. Requirement Clarification

### Functional Requirements (FR)
- Accept payments via credit cards.
- Support refunds and recurring billing.
- Expose APIs for merchants (Stripe-like).
- Webhooks to notify merchants of payment status.

### Non-Functional Requirements (NFR)
- **High Reliability**: 99.9999% uptime. Payments cannot fail due to our system.
- **Exactly-once processing**: No double charging.
- **PCI DSS Compliance**: Secure handling of credit card data.
- **Latency**: Reasonable API latency, but consistency > latency.

## 2. Back-of-the-Envelope Estimation

| Metric | Estimation | Result |
| :--- | :--- | :--- |
| **Transactions/Day** | 1 Million | 1M |
| **QPS [Queries Per Second]** | 1M / 100K | ~10 QPS (Avg) |
| **Peak QPS** | 10x Avg | ~100 QPS |
| **Storage (Transactions)** | 1M * 365 * 1KB | ~365 GB/year |

> **Interview Tip**: QPS is low, but consistency requirements are extreme. Focus the interview on reliability, atomicity, and handling edge cases (network timeouts), NOT scalability.

## 3. System Interface Definition

- `POST /v1/payments`
  - Body: `{ merchant_id, amount, currency, source_token, idempotency_key }`
  - Response: `{ payment_id, status }`
- `POST /v1/refunds`
  - Body: `{ payment_id, amount, idempotency_key }`

## 4. Database Design (Data Model)

**Relational Database (PostgreSQL / CockroachDB)** - Strict ACID guarantees.

**Payment Order Table**
- `payment_id` (PK)
- `merchant_id`
- `idempotency_key` (Unique Index)
- `amount`, `currency`
- `status`: `INITIATED`, `PROCESSING`, `SUCCESS`, `FAILED`, `REFUNDED`

**Ledger Table (Double-Entry Bookkeeping)**
- `ledger_id`
- `transaction_id` (FK to payment)
- `account_id`
- `amount`
- `entry_type`: `CREDIT` or `DEBIT`

## 6. Detailed Design (Deep Dives)

### 6.1 Idempotency: Exactly-Once Processing
Network calls can time out. If a merchant doesn't get a response, they will retry.
- **Idempotency Key**: A UUID generated by the client.
- **Process**:
  1. Lookup key in DB.
  2. If found & status is `SUCCESS`, return previous response.
  3. If found & status is `PROCESSING`, return HTTP 429 (Conflict / Retry later).
  4. If not found, create record as `INITIATED`.

### 6.2 Core Logic: Payment API Handler Pseudocode

```python
def process_payment(request):
    ikey = request.idempotency_key
    
    # 1. Check Idempotency (Atomic operation)
    payment_record = db.query("SELECT * FROM payments WHERE idempotency_key=?", ikey)
    if payment_record:
        if payment_record.status == 'SUCCESS':
            return payment_record.response
        if payment_record.status == 'PROCESSING':
            raise ConflictError("Payment already in progress")
            
    # 2. Insert new record
    payment_id = generate_id()
    db.execute("INSERT INTO payments (id, idempotency_key, status) VALUES (?, ?, 'PROCESSING')", 
               payment_id, ikey)
               
    try:
        # 3. Call External PSP (Payment Service Provider)
        psp_response = psp_client.charge(request.amount, request.token)
        
        # 4. Update status & Record Ledger
        db.begin_transaction()
        db.execute("UPDATE payments SET status='SUCCESS' WHERE id=?", payment_id)
        ledger.record_double_entry(
            debit_account=system_bank, 
            credit_account=request.merchant_id, 
            amount=request.amount
        )
        db.commit()
        
        kafka.publish("payment_success", payment_id)
        return {"status": "SUCCESS", "id": payment_id}
        
    except RetryableError as e:
        # Network timeout to PSP - must rely on Reconciliation!
        db.execute("UPDATE payments SET status='PENDING_VERIFICATION' WHERE id=?", payment_id)
        kafka.publish("payment_reconciliation_queue", payment_id)
        return {"status": "PROCESSING", "id": payment_id}
```

### 6.3 Double-Entry Bookkeeping
Every transaction involves two ledger entries that must sum to zero.
- **Debit**: Adding funds to a clearing account.
- **Credit**: Adding funds to the merchant's payable account.
Ensures absolute financial accuracy.

### 6.4 Reconciliation
If the PSP call times out, we don't know if the money moved.
- A nightly CRON job (Reconciliation Service) fetches the settlement report from the PSP.
- It compares the PSP report with our internal Ledger.
- Mismatches are flagged for manual review or automatic resolution.

## 7. Bottlenecks & Fault Tolerance

- **PSP Outages**: Use circuit breakers. Fallback to secondary PSPs if routing allows.
- **Kafka Drops**: Use WAL [Write-Ahead Logging] or the Transactional Outbox pattern. Instead of writing to DB and publishing to Kafka separately, write the event to an `outbox` table in the same DB transaction, and have a background worker poll the outbox to publish to Kafka.

## 8. Summary & Interview Tips

- **Tip 1**: Always bring up the **Transactional Outbox Pattern**. Dual writes (writing to DB + writing to Kafka) are a classic anti-pattern in payment systems.
- **Tip 2**: Mention **PCI DSS**. Say "We will isolate credit card data in a separate highly-secured tokenization vault network. The rest of the system only sees tokens."
- **Tip 3**: Emphasize idempotency. It's the most common question in a payment system interview.
